# Архитектура predel / BrandDeck

Подробности исходных слоёв: [docs/architecture.md](docs/architecture.md).

```text
PPTX → OOXML extractor → дизайн-система + каталог макетов
Контент → planner (Inference API / offline) → единый план
Краткий бриф + назначение → структура (JSON-схема) → текст каждого слайда → единый план
       → изображения: материалы + загрузки → сопоставление → (text-to-image)
       → balanced / columns / focus → native PPTX composer
       → схемы, пиктограммы, картинки в слотах шаблона
       → структурный QA → LibreOffice → PDF + HTML + PNG
       → аудит с координатами → веб-интерфейс
       → выбранные замечания → новый макет выбранных слайдов → новая версия + QA
```

- `analyzer.py`: цвета, типографика, геометрия и вместимость текстовых зон.
  Кеш версии 1.6 учитывает выходы зон за холст, позицию заголовка, пустые блоки
  макета под объект (`backdrop_area_ratio`) и специализированные
  подписи. Макет определяется по OOXML part, а не по неуникальному имени.
- `brief.py`: генерация по краткому брифу (бизнес-задача 2 ТЗ). Этап 1 — структура:
  точное число слайдов, роль, цель и тип визуала по сюжету назначения из
  `assets/deck_purposes.json` (фича, продукт, проект, инициатива). Этап 2 — текст
  каждого слайда отдельным запросом, параллельно по числу слотов сервера.
  Оба ответа ограничены JSON-схемой (`response_format`), поэтому число слайдов и
  форма визуалов гарантированы грамматикой llama.cpp/vLLM. Повторяющиеся заголовки
  и слишком длинный текст один раз возвращаются модели со списком проблем.
  Заголовок фиксируется на этапе структуры. Без модели режим недоступен.
- `planner.py`: один план содержания на набор вариантов. Семантическая роль,
  вместимость, число блоков и обязательность иллюстраций участвуют в выборе.
  План хранит объяснение выбора и альтернативы.
- `composer.py`: сохраняет исходные masters/layouts и фон. Заполняет подходящие
  текстовые зоны, сохраняет порядок чтения и нативные таблицы/диаграммы.
  Новое содержимое именуется `BrandDeck`, чтобы QA проверял его независимо от
  того, был ли блок унаследован из шаблона. После заполнения клонированного
  слайда-образца удаляются его неиспользованные леса: блоки с удалённым текстом
  образца, иконки и точки при них, фигуры под новым контентом и пустые рамки под
  фото (`layout_geometry.py`, список удалённого — `exemplar_cleanup` в манифесте).
  Если 2–6 коротких тезисов заняли бы меньше четверти слайда, а шаблон не даёт
  им видимых карточек, тезисы оформляются нативной сеткой карточек в той же зоне
  (`origin: sparse_text` и оценка заполненности в записи визуала). Оценка
  приблизительна, поэтому решает рендер: если после экспорта слайд занят меньше
  чем на четверть, его тезисы один раз пересобираются карточками
  (`layout_hint: cards`, `cards_for_underfilled_slides` в манифесте), и колода
  проверяется заново. Когда схема
  несёт весь текст слайда, декор образца в её горизонтальной полосе тоже
  удаляется. Автоповтор QA меняет макет только у слайдов с замечаниями, чтобы
  три варианта оставались различимыми.
- `service.py`: отдельные функции генерации одной колоды, трёх вариантов и ремонта.
  Исправление создаёт новую папку с `revision.parent_id`, выбранными issue IDs и
  номерами изменяемых слайдов. План остальных слайдов сохраняется.
- `exporter.py`: headless LibreOffice с отдельным временным профилем и таймаутом.
  Один PDF служит источником PNG и автономного HTML с SVG. Экспорт не меняет PPTX.
- `qa.py`, `audit.py`: структурные проверки, стабильные IDs, координаты проблем и
  список исправимых ошибок. Проверки смысла не подменяются структурным QA.
  Остатки образца проверяются сверкой с исходным шаблоном (`original.pptx`).
- `render_audit.py`: проверки на реальном PDF-рендере — контраст текста с
  перекраской в текстовые цвета темы и доля слайда под новым контентом.
- `visual_planning.py`: разрешённые типы схем, лимиты пунктов и длины текста,
  офлайн-правила из `assets/visual_rules.json` (заголовки, маркеры
  последовательности, доля сеток пиктограмм). Контракт LoRA-селектора
  (`requirements`) не меняется: схема описывается как список утверждений.
- `diagrams.py`: process, cycle, hierarchy, pyramid, funnel, matrix, icon_grid и
  векторная иллюстрация. Каждая схема — одна группа нативных фигур; цвета из
  темы с проверкой контраста 4,5:1, кегли из шкалы шаблона. OOXML SmartArt не
  создаётся: LibreOffice рендерит его только из кэша.
- `pictograms.py`, `vector.py`: 135 иконок Lucide (ISC) как `a:custGeom`
  (дуги и квадратичные кривые переводятся в кубические Безье); выбор по
  `assets/icons/keywords.json`. `icon_builder.py` пересобирает набор из
  `frontend/node_modules/lucide-react`.
- `images.py`: хранилище по хэшу, нормализация, извлечение из PPTX/DOCX/PDF и
  локальных ссылок Markdown, лексическое сопоставление со слайдами, кадрирование
  без искажений. Порядок размещения: фото примера, picture-плейсхолдер, пустая
  фоторамка, иначе половина зоны контента. Текст, заходящий на слот сбоку,
  сужается; если текст лежит поверх фото, слот не используется.
- `imagegen.py`: необязательный OpenAI-совместимый `/images/generations`
  (`IMAGE_*`), промпт `prompts/image-v1.txt`; при ошибке — иллюстрация.
- `slide_agent/jobs.py`: локальные фоновые задачи с сохранением прогресса.
- `backend/main.py`: HTTP API, ограничение путей и размеров загрузок, статический клиент.
  `slide_agent/api.py` сохраняет совместимый импорт для CLI.
- `backend/auth.py`: SQLite-аккаунты, scrypt, отзываемые HttpOnly-сессии, ограничение
  попыток входа, проверка Origin. ContextVar выбирает личный workspace на всё время
  ASGI-запроса и фонового задания; CLI сохраняет прежнюю семантику workspace.
- `frontend/`: главная, регистрация и студия с тремя вариантами, аудитом и экспортом.
  Статические ресурсы включены в Python-пакет, отдельная сборка не нужна.
  Для production остаются внешняя очередь, квоты и изоляция обработчиков документов.

Промпты находятся в `slide_agent/prompts/`; активные версии перечислены в
`prompt_config.PROMPT_FILES` (planner-v2, planner-cpu-v2, image-v1,
brief-outline-v1, brief-slide-v1; прежние v1 сохранены). Версия, SHA-256 промптов и хэш словаря пиктограмм записываются в
манифест результата; это позволяет воспроизвести конфигурацию.
Входные материалы считаются данными, инструкции внутри них не являются командами.

Ограничения: схемы строятся из нативных фигур, а не OOXML SmartArt; выбор
пиктограмм и сопоставление картинок лексические; генерация изображений только
через внешний сервер и на реальной модели не проверялась; нет семантического
VLM-аудита. Геометрический анализ и извлечение
дизайн-токенов не гарантируют равенство рендера с Microsoft PowerPoint. Неизвестный
шаблон и реальный организаторский inference требуют отдельного приёмочного прогона.
