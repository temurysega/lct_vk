## Результаты исполнения и осмотра

**Автоматические проверки.** Исходный pytest: **175 passed, 3 skipped** за 12,31 с. После подключения отдельного временного renderer выполнены именно 3 пропущенных теста: **3 passed** за 9,60 с. Это два запуска, а не заявка на единый полный прогон с LibreOffice. Ruff и TypeScript typecheck прошли, production UI собран во временную папку. Старый и актуальный UI прошли основной Chrome-сценарий; текущий — дополнительно выбор исправления. Firefox/WebKit не стартовали из-за недостающих бинарников. Время включает новый вызов jobs, ожидание и скачивание; `elapsed_seconds` внутри manifest отдельно описывает сборку. Модели нет, поэтому нельзя на основании этих чисел подтвердить официальный лимит для сценария краткого брифа.

**Экспертная проверка содержания.** Повествование полного материала связно: проблема → кому нужен ответ → решение → процесс → ограничения → пилот → метрики → запрос ресурсов. Числа 30 минут, 150 сотрудников, 2 подразделения, 6 недель, 3 человека сохранены. Утверждений о фактическом успехе ещё не проведённого пилота не добавлено. Слайды о решении и процессе частично повторяют исходный материал; это не выдано за результат смыслового переписывания моделью. Размещение фотографии специалистов соответствует теме слайда 3. Вторая картинка серверной не использована; manifest честно содержит `unplaced`, UI показывает только фактическое число изображений.

**Редактируемость и графики.** Нативные группы, text boxes, charts и tables подтверждены OOXML и операцией edit → save → reopen. Charts сохраняют editable workbook. Отдельно найден дефект читабельности pie chart после полного сервисного QA. Проверка качества графиков не выводилась из успешного ZIP или HTTP-ответа.

**Рендереры.** Превью `libreoffice-*` — реальный LibreOffice 26.2.6.3, запущенный с read-only образа во временной папке; [версия и SHA](evidence/isolated-renderer.json). `powerpoint-*` — действительный экспорт Microsoft PowerPoint/macOS, только для двух baseline balanced-колод: VK Tech и Brutalism. Исходные превью `analyzer` — **схематические**, они не использованы как подтверждение отображения в PowerPoint. LibreOffice заменяет отсутствующие шрифты; тождество его рендера PowerPoint не заявляется.

Дополнительная [буквальная сверка всех 15 колод](evidence/content-comparison-all.json) подтверждает отсутствие пропусков в PDF-тексте, но не читаемость: вертикальное письмо Onocom — наглядный контрпример ([слайд 9](additional-unseen/artifacts/unseen-onocom/focus/libreoffice-slide-09.png), [OOXML](evidence/onocom-vertical-text.json)).

## Архитектура после удаления малой модели

Коммит `f33ded5` удалил профиль Qwen2.5-1.5B + LoRA layout adapter, обучение/ноутбуки, `compose.cpu.yaml` и связанные настройки. [Состав удаления](evidence/removed-model-commit.txt). Игнорируемая локальная папка `training/` физически осталась, но не участвует в проверенном runtime. Все 35 проверенных Python-модулей импортируются; тесты/API используют текущие файлы, не удалённые модули.

Её функции теперь распределены между двумя путями:

- **Содержание:** внешний `InferenceClient` → двухэтапный `brief.py` или planner по полному тексту. Подготовленный конфиг — Qwen3.5-9B; возможно подключение совместимого сервиса через `INFERENCE_*`.
- **Дизайн и раскладка:** OOXML-токены, классификация зон и scoring в `assign_patterns`, затем composer и детерминированный QA. В offline-режиме из полного текста строится план правилами. Выбор макетов не зависит от обучения адаптера.

`INFERENCE_CONTEXT_AUDIT` по умолчанию **выключен** (`contextual_audit.py:62`), а при включении анализирует текст плана, не изображение слайда. `INFERENCE_VISION=1` у анализатора отправляет до четырёх схематических превью; точные токены берутся из OOXML. Такой этап не равен визуальному аудиту итогового PPTX. Документированная «гарантия грамматики» ограничена реальным backend: `llm.py:170` может перейти с schema на JSON mode/plain text при 400.

Неработающих импортов удалённой малой модели не выявлено. Выявлены независимые проблемы установки и устаревшие фразы об обучении. **Само отсутствие обучения не является недостатком: в ТЗ нет требования обучать модель.**

## Что показывать и что закрыть перед сдачей

**Готово к показу при подготовленном renderer/UI:** загрузка трёх VK-шаблонов, сохранение анализа, сборка 9 вариантов из готового текста, одна тематическая фотография, редактируемые фигуры/текст, скачивание PPTX/PDF/HTML, превью и визуализация реальных замечаний. Можно отдельно показать честный пример неудачного внешнего шаблона и устройство QA.

**Мешает объявить полное выполнение ТЗ:** живой бриф/model/VK inference не проверены; неизвестный шаблон не гарантирует пригодный результат; диаграммы и ремонт требуют доработки; установочный пакет теряет extractor. Для финала остаются условные требования T2I и VK inference, браузерная матрица, доступ экспертов и питч.

Три наиболее полезные группы работ: **исправить распознавание/выбор зон неизвестного шаблона; сделать воспроизводимый живой запуск с разрешённой моделью и экспортом; закрыть дефекты диаграмм и подтверждать результат выбранного ремонта**. Детальные критерии готовности — в [минимальном плане](FIX-PLAN.md).
